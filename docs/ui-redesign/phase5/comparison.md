# E4.9i-P1 方案对比与推荐

- **基准提交**：`432a43ad594c69d3236ba189a4de4ecfd0b29126`
- **对比对象**：`prototype-a.html`（概览优先） / `prototype-b.html`（知识状态优先）
- **共同前提**：两套方案都保留全部现有编辑能力，状态文案都只取服务端 `state_label`，都不新增 API / Store / 数据库字段

## 1. 六维对比

### 1.1 信息可理解性

| | 方案 A | 方案 B |
| --- | --- | --- |
| 首屏能回答什么 | 「我有几个知识点、几个要关注、下一步做什么」——一句结论 + 4 个计数 | 「哪些知识点需要处理」——列表直接给出状态与复习时间 |
| 结论句 | 有，由计数派生（`共记录 6 个知识点，其中 4 个需要关注，1 个状态稳定。`） | 有，但压缩成一行（`先处理 1 个误区，再做 1 个到期复习。`） |
| 状态含义 | 徽标 + 悬浮说明 | 徽标 + 左侧色条 + 悬浮说明 |
| 知识点详情 | 点开才出现 | 点开才出现 |
| 风险 | 概览占首屏，知识点要滚动才看到（1440×900 下第 1 条在 ~570px 处，首屏可见） | 没有「总览」概念，新用户第一次进入直接面对列表 |

**判断**：A 更利于「先知道全局」，B 更利于「直接处理待办」。

### 1.2 学习状态的可解释性

两方案相同：`state_label` 是唯一状态来源，详情里有「来源与复习」区块（系统推导 / 人工维护 / 来源不明）、诊断原文、下一步、以及「证据标识 N 个」的说明。

差异在于**暴露时机**：

- A 把「薄弱知识与复习」独立成卡，`next_actions[0]` 直接写在卡里，不需要点开。
- B 把下一步放在详情内，列表行只给状态与日期。

对「我应该采取什么下一步行动」这个目标问题，**A 的答案更显眼**；对「哪些知识薄弱」，**B 的列表更紧凑**。

### 1.3 操作效率

| 任务 | 方案 A | 方案 B |
| --- | --- | --- |
| 找「需要复习的知识点」 | 看概览计数 → 滚到知识区 → 逐行读徽标 | 点「待复习」筛选 → 只剩相关行 |
| 编辑摘要 | 概览卡右上「编辑摘要」 | 滚到页面底部「编辑摘要」 |
| 编辑某个知识点的诊断 | 展开行 → 编辑 | 展开行 → 编辑 |
| 只看稳定的知识点 | 无筛选，逐行扫 | 点「稳定」筛选 |
| 从薄弱点去练习 | 薄弱卡内「去练习」按钮，一步 | 展开详情 → 「去练习」，两步 |

**判断**：B 在「按状态筛查」上明显更快（这是知识点数量增长后最常用的动作）；A 在「直接行动」上更快。

### 1.4 页面复杂度

| | 方案 A | 方案 B |
| --- | --- | --- |
| 全部课程卡片数 | 6（概览 / 知识 / 薄弱 / 目标 / 误区 / 偏好） | 6（计数条 / 知识 / 目标 / 误区 / 摘要 / 偏好） |
| 首屏信息块 | 1 个大卡 | 1 条 + 1 个大卡 |
| 新增交互 | 无 | 状态筛选（6 个 chip） |
| 视觉噪声 | 4 个统计块 + 结论句，密度中等 | 左侧色条 + 3 行事实，每行更高 |
| 与现有页面的距离 | 较近（保留概览统计块） | 较远（统计块降级为计数条，摘要下移） |

B 引入筛选器是唯一的**新增交互面**，但也因此多一处需要维护的选中态（`aria-pressed`）。

### 1.5 现有功能兼容性

| 现有能力 | A | B |
| --- | --- | --- |
| 编辑摘要（脏缓冲 / 取消确认 / 失败保留） | 保留，位置不变 | 保留，位置下移 |
| 目标增删改 | 保留 | 保留 |
| 知识点掌握度 / 诊断 / 下一步编辑 | 保留 | 保留 |
| 误解状态 / 严重度 / 修复策略编辑 | 保留 | 保留 |
| 偏好 chip 编辑 | 保留 | 保留 |
| 课程范围切换 | 保留 | 保留 |
| 课程视图只读边界 | 保留 | 保留 |

两者兼容性相同。B 需要额外确认：**摘要移到列表之后**是否影响 `LearnerProfilePanel.summary.test.tsx` 的定位（测试用 `getByText` / `getByRole`，不依赖顺序，应当不受影响，但需实跑）。

### 1.6 预计代码修改范围

| | 方案 A | 方案 B |
| --- | --- | --- |
| 新增组件 | `ProfileConclusion`、`WeakKnowledgeSection` | `CompactCountStrip`、`KnowledgeFilterBar`、`KnowledgeList` |
| 拆分 `LearnerProfilePanel` | 中等（摘要拆出，知识行拆出） | 较大（摘要下移，知识列表独立成页主体） |

## 3. 推荐

### 推荐方案 A「概览优先」，但吸收 B 的筛选器

**理由**：

1. **页面目标首先是「读学习情况」，不是「管理知识点」。** 方案 A 用一句结论回答「我学得怎么样、下一步做什么」，这正是任务书列出的问题 1–6 中最难回答的两个（问题 5「为什么」和问题 6「下一步」）。B 把这些藏在详情里，需要点开才看到。
2. **与现有页面距离更近。** A 保留概览统计块与摘要的位置，P2 是「重排 + 修语义」，不是「重建信息架构」。B 把摘要移到列表底部、统计降级为一条 strip，会让现有 `LearnerProfilePanel.summary.test.tsx` 的语义更依赖位置，回归风险更高。
3. **课程视图的一致性。** 课程视图本来就是「课程卡 → 目标 → 知识 → 薄弱」的顺序，A 的结构与它同构，两个视图可以共用同一批组件（`KnowledgeList` + `WeakKnowledgeSection`）。B 的课程视图需要在课程卡和列表之间插入计数条，层级更多。
4. **筛选器确实有价值。** 知识点增长到 10+ 后，「只看待复习」比逐行扫描快得多。因此建议 **在 A 的知识卡头部加入 B 的状态筛选 chip**——它只是 `KnowledgeSection` 内部的一处过滤，不影响整体结构。

**综合方案（推荐）**：

```text
我的学习档案
├── 页面头：标题 + 副标题（按范围变化） + 课程范围选择
├── 学习概览
│   ├── 结论句（由计数派生，注明「不含模型推测」）
│   ├── 4 个计数：活跃目标 / 已记录知识点 / 已到期复习 / 未解决误区
│   └── 画像摘要（阅读态 / 编辑态）
├── 知识掌握情况
│   ├── 状态筛选 chip（全部 / 需要关注 / 待复习 / 存在误区 / 稳定 / 证据不足）
│   └── 知识行：名称 · 领域 · [状态] · 证据标识 N 个 · 复习日期 · 展开
│       └── 详情：掌握度参考 / 来源与复习 / 诊断 / 下一步 / 去练习 / 编辑
├── 薄弱知识与复习（next_actions 直出 + 去练习）
├── 学习目标
├── 误解记录
└── 学习偏好
```

这套组合的修改范围介于 A 与 B 之间，但收益最大：结论优先、可筛选、与课程视图同构。

## 5. 需要在 P2 开始前由产品确认的三件事

1. **全部课程视图是否应显示「已到期复习」的服务端计数。** 当前前端按 `review_due_at <= now` 自算（`analysis.md` §2.3），课程视图有服务端 `knowledge.due_reviews`，全部课程视图没有。P2 若改用 `state_label === "review_due"` 计数，与课程视图口径一致，但数值可能与「到期时间」不同。
2. **编辑知识点后是否保留「人工维护」徽标。** 服务端会把 `origin` 改为 `manual` 并停止重算，界面必须如实告知；这是产品语气问题（是否显得「系统不再管这个知识点了」）。
3. **是否允许前端把 `course_id` 映射为课程名称。** 目前 `knowledge_states` 只有 id；映射需要读 `coursesStore.courses`。这属于前端拼装，需确认是否符合「课程范围由服务端过滤」的冻结规则。

## 6. 本阶段结论

- 两套原型均已完成 10 个必需场景、深浅主题、四档视口，并经过 DOM 实测（无横向溢出、保存失败保留输入、键盘可展开）。
- 推荐 **方案 A + 状态筛选**。
- 现有页面最需要修的**不是布局**，而是**状态语义**：`masteryStateFor` 与 `state_label` 并存导致同一知识点显示不同结论（已在真实数据上复现）。P2 应先做 P2-1，再做视觉重排。
- 未修改任何业务代码、API、Store 或数据库字段；`npm run build` 与既有测试的基线见 PR 描述。
